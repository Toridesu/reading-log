# ADR-0001：初期アーキテクチャと検証順序

日付：2026-11-11（日本時間）

状態：初期提案の記録。アプリ・認証・アカウント・外向き通信の判断は[ADR-0002](0002-go-and-oidc.md)で更新。AWSを当面作成しない進め方は継続する。

## 背景

読書管理アプリを題材に、クラウド設計・構築・運用からCI/CD、脅威検知・対応へ段階的に学ぶ。利用者は関連技術の多くに触れた経験があり、言語の指定はない。当面は料金による制約を設けず、コードと定義を準備してからAWSへ少しずつ展開する。

## 判断とトレードオフ

| 論点 | 初期提案 | 理由と代替案 |
| --- | --- | --- |
| アプリ | Djangoとサーバー側テンプレート | 認証・フォーム・ORM・マイグレーションをまとめて扱える。FastAPI + SPAはAPIとUIを独立させやすいが、今回は実装・認証境界が増える |
| 認証 | Django標準認証とDBセッション | 小さなCRUDアプリに合い、認証と所有者による認可を学べる。CognitoはMFA・認証基盤の運用を委譲できる一方、OIDC連携と通信経路の検討が増える |
| アカウント | 管理コマンドで作成 | 初期のユーザー登録・メール送信・アカウント復旧の範囲を抑える。一般公開へ進める際は登録・復旧・MFAの要件を再検討 |
| 認可 | すべての操作で所有者をサーバー側で確認 | ログイン済みであることと、そのタスクを操作できることを分離する。クライアントの所有者指定やUI上の非表示を根拠にしない |
| 配置 | パブリックALB、プライベートFargate/RDS | リクエスト経路とAWSサービスへの起動時通信を区別して学べる。パブリックFargateは費用上の代替案として記録 |
| 外向き通信 | ECR API・Registry、Logs、SecretsのInterface Endpoints + S3 Gateway | 最小版は実行中に外部APIを必要としない。外部サービスの導入時にNATとの比較をやり直す。エンドポイントは必ずしも安価ではない |
| 可用性 | 2AZのネットワーク、アプリ1タスク、RDS Single-AZ | まず業務機能と運用の最小構成を完成させる。高可用性を保証する構成ではなく、冗長化は後続の学習対象 |
| 適用時期 | ローカル実装・検証を先行 | AWS実機を作成しない利用者指定。IAMやRDS復元等の確認を完了扱いにせず、実展開後の検証として残す |

Django標準認証を使っても、アプリ固有の所有者判定、公開時のセキュリティ設定、ログイン試行制限は別に実装・検証する。Cognitoを採用した場合もタスクの所有者判定は必要である。

## 再検討する条件

- 習熟した言語・フレームワークを優先したいという希望が出た場合。
- 一般公開、MFA、外部IdP、ユーザー登録や復旧が必要になった場合。
- 書籍検索やメール等の外部通信を実行時に追加する場合。
- 実際のAWS展開時に予算・可用性・稼働時間が確定した場合。
